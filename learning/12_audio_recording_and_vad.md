# 音の扱い方 — 録音・音量（dB）・VAD

> 対象読者: 音を扱うアプリを初めて作る人。Web開発の経験はあるが、音声信号は未経験。
> ねらい: **「いま喋っているか」をプログラムで判定する**ために必要な基礎を押さえる。
> 本アプリでの設計は [docs/01c](../docs/01c_app_client.md) §3、
> 実機で分かったことは [pre-research/handsfree/FINDINGS.md](../pre-research/handsfree/FINDINGS.md)。

## 1. 音はどうやって数値になるか

音は**空気の振動**（波）。マイクはこれを電気信号に変え、**一定間隔で数値として記録**する。

| 用語 | 意味 | Webでいうと |
|---|---|---|
| **サンプリングレート** | 1秒間に何回測るか（Hz） | 動画のフレームレートに近い |
| **振幅（amplitude）** | ⚠️ **波の高さ＝音の大きさ** | — |
| **量子化ビット数** | 振幅を何段階で表すか | 画像の色深度に近い |

本アプリは **16,000 Hz・16ビット・モノラル**で録音している。

- **16,000 Hz** — 人の声はこれで足りる（電話は 8,000 Hz）
- **16ビット** — 振幅を **-32768〜32767** の整数で表す
  （⚠️ **この 32767 が後で効いてくる**）
- **モノラル** — 音声認識にステレオは要らず、素直にサイズが半分になる

📌 **選定の基準は「音楽的な良さ」ではなく「認識に足りるか」と「通信量」。**
走行中は電波が細いので、送るものは小さいほどよい。

## 2. デシベル（dB）— ⚠️ 「絶対的な大きさ」ではない

⚠️ **ここが最初の落とし穴。** 日常で「60デシベルの騒音」のように使うので
**絶対的な単位**だと思いがちだが、**デシベルは「基準の何倍か」を表す比**にすぎない。
**基準を決めないと意味が決まらない。**

### dBFS — 基準を「機械の限界」に取ったもの

プログラムで音量を扱うときに出てくるのは、たいてい **dBFS**（decibel Full Scale）。
**基準は「その機械が表現できる最大の音」**（＝振幅 32767）。

| 値 | 振幅 | 意味 |
|---|---|---|
| **0 dBFS** | **32767** | ⚠️ **限界。これ以上は表現できない** |
| -20 dBFS | 約 3277 | 限界の 1/10 |
| -40 dBFS | 約 328 | 限界の 1/100 |
| -60 dBFS | 約 33 | 限界の 1/1000 |

```
静か ←─────────────────────────────→ うるさい
-160        -60        -40        -20         0
 無音      ヒソヒソ    普通の声    大きい声   限界
```

⚠️ **上限が 0 で、静かなほどマイナスに深くなる。プラスの値は出てこない。**
日常の「60デシベル」とは**符号の向きが逆**なので、頭を切り替える必要がある。

### なぜ対数（dB）を使うのか

人間の耳は**音の大きさを比で感じる**（振幅が2倍で「2倍うるさい」とは感じない）。
振幅をそのまま扱うより、⚠️ **対数にしたほうが人間の感覚に近く、扱う桁数も小さくなる。**

変換式はこれ:

```
dBFS = 20 × log10(振幅 ÷ 32767)
```

## 3. ⚠️ 飽和（クリッピング）— 情報が消える

**大きすぎる音が来ると、32767 を超えた分は記録できず、頭が平らに潰れる。**
これを **飽和** または **クリッピング** と呼ぶ。

```
本当の音の波形              記録される波形
     /\                        ┌─┐   ← 32767 で頭が切れる
    /  \                      /   \
───/────\───  32767 ────────/─────\──────
  /      \                  /       \
```

⚠️ **飽和した状態では、音が増えても値が変わらない。** すでに天井だから。

📌 **これは「音が割れる」という音質の問題ではなく、「情報が消える」という問題。**
⚠️ **消えた情報は、後からどう計算しても復元できない。**
音量を見て何かを判定するプログラムでは、**飽和は致命的**になる。

## 4. VAD（音声区間検出）

**VAD** = Voice Activity Detection。**「いま人が喋っているか」を判定する技術**の総称。
日本語では「音声区間検出」。

音声を扱うアプリでは、たいてい必要になる:

- **喋り終わったら自動で送信する**（本アプリの用途。⚠️ **走行中は画面を触れない**）
- 無音部分を切り詰めて通信量を減らす
- 録音を発話ごとに区切る

### 作り方は大きく2種類

| 方式 | 判定材料 | 特徴 |
|---|---|---|
| **音量ベース** | **音の大きさ** | ⚠️ **作るのは簡単だが、騒音に弱い** |
| **音声らしさベース** | **周波数の特徴** | 作るのは難しいが、騒音に強い |

#### なぜ周波数を見ると強いのか

音は**高さ（周波数・Hz）**を持ち、⚠️ **音の種類によって「どの高さに集まっているか」が違う。**

| 音 | だいたいの周波数 |
|---|---|
| **エンジン音・風切り音・空調** | ⚠️ **低い**（数十〜数百 Hz） |
| **人の声** | **300〜3400 Hz**（電話がこの範囲だけ通す設計） |

📌 **周波数で見れば、騒音と声は別の場所にいる。**
だから「低い音だけ削れば、声を残して騒音を消せる」。

⚠️ **一方、音量ベースは「全部の周波数を合計した大きさ」しか見ない。**
騒音と声を足した結果が1個の数字になるので、**分離できない。**

## 5. 実装: Androidで音量を取る

`expo-audio` では `isMeteringEnabled: true` を立てると
`recorder.getStatus().metering` に **dBFS** が入る。

中身は Android の **`MediaRecorder.getMaxAmplitude()`** で、
ライブラリがこう変換している:

```kotlin
// expo-audio / AudioRecorder.kt
val amplitude = recorder?.maxAmplitude ?: 0
return if (amplitude == 0) -160.0 else 20 * log10(amplitude.toDouble() / 32767.0)
```

### ⚠️ 落とし穴が3つある

#### ① `maxAmplitude` は読むとリセットされる

返るのは「**前回読んでからの最大値**」。つまり:

- ⚠️ **ポーリング間隔が、そのまま測定窓になる**（100ms間隔なら「直近100msのピーク」）
- ⚠️ **読む場所を1箇所に限る必要がある。**
  2箇所から読むと**値を奪い合い**、双方が実際より小さい音量を見て誤検知する

#### ② `-160` は「無音」ではなく「測れなかった」

上のコードのとおり、⚠️ **`maxAmplitude` が 0 のとき `-160` を返す。**
これは実測値ではなく**番兵（sentinel）**で、こういうときに出る:

- **録音開始直後**（「前回」が無いので測る材料がない）
- **読み取りに失敗したとき**（`catch` で 0 に落ちる）

⚠️ **これを「完全な無音」と解釈すると壊れる。**
本アプリでは実際に、⚠️ **録音開始 109ms の `-160` が1回出ただけで騒音ガードが無効化された。**

**対策は2つ:**

| | 中身 |
|---|---|
| **ウォームアップ** | 最初の一定時間（300ms）の値は使わない |
| **継続判定** | ⚠️ **1サンプルで判断せず**、一定時間（500ms）続いて初めて数える |

📌 **本質は継続判定の方。** 読み取り失敗が1回起きるだけで判定が壊れるのは、脆すぎる。

#### ③ ⚠️ 「ピーク1個」に潰すと、周波数の情報が全部消える

**これが最も重要。** `maxAmplitude` は**その窓の中で一番大きかった値**しか返さない。

```
実際の音     = エンジンの低い音（大きい） + 人の声（小さい）
maxAmplitude = 大きい方だけ  ← ⚠️ 声の情報が消える
```

⚠️ **§4 で見たとおり、騒音と声は周波数では分離できる。**
**だがピーク1個に潰した瞬間、その分離は使えなくなる。**

## 6. 実例: 本アプリで音量ベースVADが破綻した話

📌 **教科書的な失敗なので、記録として残す。**

### 起きたこと

| 状況 | `metering` の値 |
|---|---|
| エンジン停止（インカム接続） | **-60 dB 程度** ✅ 正常 |
| **エンジン始動** | ⚠️ **0 dB 付近**（＝飽和） |
| エンジン始動＋**発話** | ⚠️ **ほとんど変化なし** |
| **録音ファイルを聞く** | 📌 **エンジン音は薄く、声は明瞭** |

### ⚠️ 「測っている音」と「ファイルの音」が違う

最後の行が奇妙に見えるが、経路を追うと矛盾しない:

```
インカムのマイク
      │
  ゲイン段（増幅）  ← ⚠️ ここで天井まで増幅されて飽和
      │
      ├──────────────────┐
      ▼                    ▼
 maxAmplitude        ノイズキャンセル（DSP）
 （ピーク1個）              │
      │                    ▼
      ▼               録音ファイル
 ⚠️ 0 dBFS 固定     ✅ 低い音が削られ、声が明瞭
```

⚠️ **音量計はノイズキャンセルを通る前を見ている。**
だから「**聞けば良好、測れば飽和**」という食い違いが起きた。

### 学べること

> 📌 **教訓1: 音量ベースのVADは、騒音環境では原理的に成立しないことがある。**
> 閾値の調整・相対判定・移動平均といった**工夫は、飽和した値には一切効かない**
> （⚠️ **変化しない値からは、何も引き出せない**）。

> 📌 **教訓2: 「録音が綺麗＝音量計も正しい」ではない。**
> ⚠️ **音の加工がどの順で行われ、自分が見ている値がどの段階のものか**を意識する。

> 📌 **教訓3: 静かな場所での成功は、騒音下での成功を意味しない。**
> 本アプリは停車中に成立を確認していたが、⚠️ **エンジンをかけた瞬間に破綻した。**
> **実環境で試すまで「動く」と言ってはいけない。**

## 7. 参考: `audioSource` — 録音の「用途」を伝える

Androidでは録音時に**用途**を指定でき、⚠️ **用途によって端末側の音の加工が変わる。**
`expo-audio` では `android.audioSource` で指定する（⚠️ **トップレベルではない**）。

| 値 | 用途 | 加工 |
|---|---|---|
| `mic`（既定） | 汎用 | 少ない |
| `voice_recognition` | **音声認識** | ノイズ抑制あり・⚠️ **AGCは切られるのが一般的** |
| `voice_communication` | 通話 | ノイズ抑制・エコー除去・**AGCあり** |
| `unprocessed` | 生の音 | ⚠️ **一切なし** |

**AGC**（Automatic Gain Control・自動ゲイン調整）＝
**小さい音は増幅し、大きい音は抑える**自動調整。
⚠️ **これが騒音を天井まで持ち上げて飽和を招くことがある**ので、
**音量を見て判定するなら AGC は邪魔になりうる。**

📌 **Bluetooth経由（インカム等）の場合、音は既に機器側で加工されてから届く**ので、
⚠️ **端末側の設定が効く余地は小さい。**

## 8. まとめ

| 押さえること | ⚠️ 注意 |
|---|---|
| **dBFS は 0 が上限、静かなほどマイナス** | 日常のデシベルと符号が逆 |
| **飽和すると値が動かなくなる** | ⚠️ **情報が消えるので復元不可** |
| **`maxAmplitude` は読むとリセット** | 読む場所は1箇所に限る |
| **`-160` は「測れなかった」の番兵** | ⚠️ 無音と混同しない。1サンプルで判断しない |
| **ピーク1個に潰すと周波数が消える** | ⚠️ 騒音と声を分離できなくなる |
| **音量ベースVADは騒音に弱い** | 静かな場所での成功を過信しない |
