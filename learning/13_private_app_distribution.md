# 13. 指定した人にだけアプリを配る（限定配信）

> 調査: 2026-09-10
> ⚠️ **この文書は選択肢の整理まで。** どれを採るかは未決（決めたら `adr/` に書く）。

**不特定多数への公開ではなく、「この人たち」と決めた相手にだけ配りたい**場合の手段を整理する。

📌 **Webでいうと**「社内向けステージング環境をBasic認証で配る」のに近い。
⚠️ **しかしモバイルには「URLを教えるだけ」で済まない事情がある**（下記 §1）。

---

## 1. ⚠️ まず前提：2026年からAndroidの配布ルールが変わる

**ここが今回いちばん重要**なので最初に置く。

### 1.1 「野良APKを配る」が将来使えなくなる

Googleは**開発者確認（developer verification）**を導入した。
⚠️ **確認されていない開発者のアプリは、認証済みAndroid端末にインストールできなくなる。**

| 時期 | 何が起きるか |
|---|---|
| **2026年9月** | ブラジル・インドネシア・シンガポール・タイで**先行適用** |
| **2027年** | ⚠️ **全世界へ拡大** |

📌 **対象は「認証済みAndroid端末」**（中国以外のAndroidの約95%）で、
⚠️ **Play ストア経由でも、他のストアでも、直接APK配布でも同じく適用される。**

📌 **日本は2026年9月の先行4カ国に入っていない**ので、**いますぐ動かなくなるわけではない。**
⚠️ **ただし2027年には来る**ので、⚠️ **いま「APKを手渡し」で組むと作り直しになる。**

### 1.2 完全に塞がれるわけではない

**サイドロード自体は残る**が、**摩擦が付く**:

- 警告画面が出る
- ⚠️ **`adb` や「上級者向け」の経路では24時間の待機**が入る

📌 **開発者本人（自分の端末にadbで入れる）は今後も困らない。**
⚠️ **他人に配るには向かない**（相手に24時間待たせる・警告を突破させるのは無理がある）。

### 1.3 📌 無料の「限定配信」アカウントがある（今回の本命候補）

⚠️ **これは見落としやすいが、今回の用途にほぼ一致する。**

| | 限定配信（limited distribution） | 通常（full distribution） |
|---|---|---|
| **登録料** | ✅ **無料** | $25（1回のみ） |
| **政府発行の身分証** | ✅ **不要** | 必要 |
| **配布できる端末数** | ⚠️ **20台まで** | 無制限 |
| **アプリ数** | 無制限 | 無制限 |

> 公式の説明: 「限定配信は、**学生・趣味の開発者**、または
> **信頼できる限られた相手のためにアプリを作りたい人**に向いている」

📌 **「指定した人にだけ」という今回の要件そのもの。**
⚠️ **ただし20台という上限**があるので、**配る相手が増える見込みなら通常アカウントにする。**

## 2. 選択肢の一覧

| | 手段 | 費用 | 相手の手間 | アクセス制御 |
|---|---|---|---|---|
| **A** | **Google Play 内部テスト**（internal testing） | 無料〜$25 | ストアから普通に入る | ✅ **メールで指定** |
| **B** | **Firebase App Distribution** | ✅ 無料 | 招待メール→専用アプリ | ✅ **メールで指定** |
| **C** | **EAS Build の internal distribution** | 無料枠あり | リンクから入れる | ⚠️ **既定はURLを知る全員** |
| **D** | **APKを手渡し**（いまと同じ） | ✅ 無料 | ⚠️ 提供元不明の許可 | ❌ **無い** |

📌 **A・B・C はいずれも「Playストアの審査」とは別物**（審査待ちが無い、または軽い）。

---

## 3. A. Google Play 内部テスト（internal testing）

**Play Console の「内部テスト」トラックに上げ、メールアドレスで配る相手を指定する。**

| 項目 | 内容 |
|---|---|
| **人数** | ✅ **100人まで** |
| **審査** | ✅ **通常のアプリ審査を待たない**（アップロード後すぐ配れる） |
| **相手の手間** | ✅ **最小。** 招待リンクを一度開けば、**あとはPlayストアから普通に更新される** |
| **アクセス制御** | ✅ **メールアドレスで指定**（リストまたはCSV） |

### ⚠️ 「12人・14日間」のルールは内部テストには適用されない

**ここが混同しやすい。**

2023年11月13日以降に作った**個人**開発者アカウントは、
**本番公開（production）するために「12人のテスターを14日間continuously」**という条件がある。

⚠️ **しかしこれは「クローズドテスト」の条件で、内部テストには課されない。**
公式には**内部テストは「アクセスに要件なし」**と明記されている。

📌 **つまり「本番公開はしない、内部テストのまま使い続ける」なら12人は要らない。**
**今回の用途（指定した人にだけ）なら、そもそも本番公開する必要がない。**

### 相手側の体験

1. 招待リンクを開いて「テスターになる」を押す（一度だけ）
2. ⚠️ **Playストアのアカウントは、招待したメールアドレスと同じものが必要**
3. 以降はPlayストアのアプリとして扱われる（**自動更新される**）

📌 **「提供元不明のアプリを許可」が要らない**のが大きい。
⚠️ **§1 の開発者確認も、Play経由なら（アカウントを確認済みにすれば）問題にならない。**

---

## 4. B. Firebase App Distribution

**Firebaseのコンソール（またはCLI）からAPKを上げ、テスターをメールで招待する。**

| 項目 | 内容 |
|---|---|
| **費用** | ✅ **無料**（Sparkプランに含まれる） |
| **審査** | ✅ **無し** |
| **アクセス制御** | ✅ **メールで招待。グループ分けもできる** |
| **相手の手間** | ⚠️ **中。** 招待を受けて、**専用のテスターアプリ経由**で入れる |

📌 **開発者向けのツールなので、配信の細かい制御（グループ・リリースノート）がしやすい。**
⚠️ **一方で「アプリを入れるための別のアプリ」が要る**ので、
**相手がITに不慣れだと説明が増える。**

⚠️ **§1 の開発者確認からは逃れられない。** Firebase App Distribution は
**Playストアではない**ので、⚠️ **2027年以降は「未確認の開発者のAPK」として扱われる可能性がある。**
📌 **配信の仕組みと、開発者確認は別の話**なので、
**Firebaseを使うとしても開発者アカウントの確認（§1.3）は別途必要**と考えるべき。

## 5. C. EAS Build の internal distribution

**いま使っているExpoの仕組みで、`eas build` にAPKを作らせてリンクで配る。**

```json
// eas.json
{ "build": { "preview": { "distribution": "internal", "android": { "buildType": "apk" } } } }
```

| 項目 | 内容 |
|---|---|
| **費用** | 無料枠は**月15ビルド**（Android）。以降は有料 |
| **iOSのUDID登録** | ✅ **Androidには不要**（iOSのad hocだけの話） |
| **相手の手間** | ✅ **小。** リンクを開いてダウンロード |
| **アクセス制御** | ⚠️ **既定は「URLを知っている人全員」**（32文字のUUID） |

### ⚠️ 既定ではアクセス制御が無い

**URLを知る誰でも入れられる**（推測は難しいが、**転送されたら止められない**）。

📌 **プロジェクト設定で
「Unauthenticated access to internal builds」を無効にすると、
Expoアカウントでのサインインを要求できる。**
⚠️ **その場合、相手にExpoアカウントを作らせて、プロジェクトに招待する必要がある。**

📌 **いまのビルド手順（ローカルで `assembleRelease`）とは別物。**
⚠️ **EASはクラウドでビルドする**ので、**ビルドを手元でやる必要が無くなる**利点はある。
⚠️ **ただし `CLAUDE.md` の「モバイルは必要最低限」からすると、
新しい依存（EASの有料枠・アカウント管理）を増やす判断になる。**

## 6. D. APKを手渡し（いまと同じ方式）

**ビルドしたAPKをそのまま渡す**（メール・クラウドストレージ・USB）。

| 項目 | 内容 |
|---|---|
| **費用** | ✅ 無料・仕組みも不要 |
| **アクセス制御** | ❌ **無い。** 渡したファイルは自由に再配布できる |
| **相手の手間** | ⚠️ **大。「提供元不明のアプリ」の許可が要る** |
| **更新** | ⚠️ **毎回配り直し。** 相手が古い版を使い続けても気づけない |
| **将来** | ⚠️ **§1 で2027年に塞がれる方向** |

⚠️ **人数が少なくても、これは勧められない。**
**更新を配り続ける手間**と、**§1の期限**が理由。

---

## 7. ⚠️ 配信方式とは別に決めないといけないこと

**どの手段を選んでも、本アプリ固有の問題が3つ残る。** ⚠️ **配信の仕組みだけでは解決しない。**

### 7.1 ⚠️ 署名キーストアを作り直す必要がある

**いまは debug のキーストアで署名している**（`App/SETUP.md`）。
📌 **自分の端末に上書きインストールするためにそうしてある。**

⚠️ **Playストアに上げるなら、専用の署名鍵が要る**（debug鍵では受け付けられない）。
⚠️ **鍵を失うと以降アップデートを配れなくなる**ので、**保管方法まで決めること。**

### 7.2 ⚠️ APIキーとクォータの設計が「1人前提」になっている

**いまは APIキー1本 + Usage Plan で、対象は「自分のAndroidだけ」**（`docs/01` §8）。

⚠️ **人が増えるとここが破れる:**

- **キーを共有する** → ⚠️ **誰が使ったか分からない。1人が使い切ると全員止まる**
- **人ごとにキーを発行する** → 誰がどれだけ使ったかは分かるが、**発行と配布の手間**が増える

⚠️ **`docs/00_user_stories.md` §5 で「複数ユーザー対応」は「やらないこと」**に入っている。
📌 **配信するなら、この線をどう引くかを先に決める必要がある**（スコープの話なので `docs/00` 側）。

⚠️ **費用が自分に来る**点も忘れないこと（Bedrock・AgentCore・Transcribe・Pollyは従量課金で、
**AgentCoreはアイドル中も課金される**）。

### 7.3 ⚠️ 相手の端末で手動設定が要る

**配信しても、そのままではハンズフリーが動かない:**

| 必要な操作 | なぜ |
|---|---|
| `設定 > アプリ > Google > デフォルトをクリア` | ⚠️ **これをしないとボタンでGoogleが開く**（[adr/006](../adr/006_handsfree_launch_mechanism.md)） |
| APIキーの入力 | アプリの設定画面 |
| 戻り先アプリの選択 | 既定は「戻らない」 |
| インカムのペアリング | 端末側 |

📌 **手順書が要る。** ⚠️ **相手がインカムを持っていないと、そもそも中核機能が試せない。**

---

## 8. 📌 整理：どう考えるか

**判断の分かれ目は「相手の人数」と「相手のITへの慣れ」。**

| もし… | 向いているのは |
|---|---|
| **相手が数人・20台以内で、手間を最小にしたい** | **A（Play内部テスト）＋ §1.3の無料アカウント** |
| **相手が開発者で、細かく配信を制御したい** | **B（Firebase App Distribution）** |
| **すでにEASを使う気があり、リンクで手早く配りたい** | **C（EAS internal distribution）** |
| **一時的に1〜2人へ見せるだけ** | **D（手渡し）**。⚠️ **恒久的な手段にはしない** |

⚠️ **「配信の仕組み」より §7 の方が重い。**
**Aを選べば配信自体は数十分で済む**が、
⚠️ **署名鍵・APIキー・手順書は、どれを選んでも自分で用意することになる。**
