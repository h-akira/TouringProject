# 15. アプリの配信を自動化する（ストアへの自動アップロード）

**「手元でビルドして、ストアの画面にドラッグする」を、コマンド（やCI）に任せる話。**
署名やAABそのものは [14](14_android_app_signing_and_release.md)、配信手段の選び方は [13](13_private_app_distribution.md)。

> **Webとの対応**: Webなら **S3に `aws s3 sync` すれば配信完了**。
> ⚠️ **アプリはストアという「他人のシステム」を経由する**ので、
> **そこにAPIで話しかける**ことになる。⚠️ **やることは増えるが、考え方は同じ。**

## 1. ⚠️ そもそも何を自動化するのか

**ストアへの提出は、突き詰めると3工程しかない。**

```
① ビルド        ソース → AAB（⚠️ 署名もここ）
② アップロード   AAB → ストアのサーバ
③ 公開          「テスターに配れ」と指示する
```

📌 **手でやると、②③がブラウザ作業になる。** ⚠️ **①も数分かかる。**
**自動化とは、この3つをコマンドに置き換えること。**

## 2. ストアのAPI

**Google Play には [Play Developer API](https://developers.google.com/android-publisher/getting_started) がある。**
⚠️ **AWSのAPIを叩くのと同じ**で、HTTPで操作する。

### ⚠️ 「Edit」というトランザクション

**ここが独特なので、先に理解しておくと迷わない。**

⚠️ **1回のアップロードは、単発のリクエストではない。**
**「編集セッション（edit）」を開いて、変更を積んで、最後にまとめて確定する。**

```
insert  → 編集セッションを開く（⚠️ この時点では本番に影響しない）
upload  → AABを送る、トラックを指定する、リリースノートを書く
commit  → ⚠️ ここで初めて全部が反映される
```

📌 **DBのトランザクションと同じ発想。**
⚠️ **「AABは新しいのに説明文が古い」といった中途半端な状態を防ぐ**ためにこうなっている。

⚠️ **commit しなければ何も起きない**ので、**途中で失敗しても壊れない。**

> 📌 **後述のツールは、どれもこの流れを代わりにやってくれるだけ。**
> ⚠️ **中で起きていることは全部同じ。**

### ⚠️ 初回だけは手で上げる必要がある

⚠️ **APIは「すでに存在するアプリ」しか更新できない。**
**パッケージ名がストアに登録されるまで、APIは相手にしてくれない。**

📌 **つまり「1回目は必ず手動、2回目から自動」**という順番になる。
⚠️ **これはツール選びの問題ではなく、APIの制約。**

## 3. 誰がAPIを叩くのか（サービスアカウント）

⚠️ **CIは「人間のアカウント」でログインできない**（パスワードも2段階認証も無理）。

📌 **そこで「プログラム用のアカウント」を作る。** これが**サービスアカウント**。

> **AWSでいうと**: 📌 **IAMロール**に近い。
> ⚠️ **人ではなくプログラムに権限を与える**という発想が同じ。

| | |
|---|---|
| **作る場所** | ⚠️ **Google Cloud**（⚠️ **ストアの管理画面とは別のサービス**） |
| **認証の材料** | **JSONファイル**（⚠️ **鍵そのもの。漏らせない**） |
| **権限の与え方** | ⚠️ **ストア側の管理画面で「ユーザー」として招待**する |

⚠️ **権限は絞る。** 📌 **「テスト用トラックへのアップロードだけ」にしておけば、
仮に漏れても本番公開はされない。**

⚠️ **作ってすぐには使えないことがある**（Google側の反映に時間がかかる）。

## 4. CI（GitHub Actions）とは

**「pushされたら、用意しておいた手順を自動で走らせる」仕組み。**

> **AWSでいうと**: 📌 **CodeBuild + CodePipeline** に相当する。
> ⚠️ **`buildspec.yml` が `.github/workflows/*.yml` になっただけ**と考えてよい。

| CodeBuild | GitHub Actions |
|---|---|
| `buildspec.yml` | `.github/workflows/<名前>.yml` |
| ビルド環境（イメージ） | **runner**（`ubuntu-latest` 等） |
| Parameter Store / Secrets Manager | ⚠️ **GitHub Secrets**（後述） |
| CloudWatch Logs | 画面上のログ |

**基本の形:**

```yaml
on:                       # ⚠️ いつ走るか
  push:
    tags: ['v*']          # タグがpushされたとき
jobs:
  release:
    runs-on: ubuntu-latest   # どこで走るか
    steps:
      - uses: actions/checkout@v4   # 既製の部品を使う
      - run: ./gradlew bundleRelease  # コマンドを実行する
```

### 📌 `uses` と `run` の違い

| | |
|---|---|
| **`run`** | ⚠️ **シェルコマンドをそのまま実行**する |
| **`uses`** | ⚠️ **他人が作った部品（Action）を呼ぶ。** 📌 **npmパッケージのようなもの** |

⚠️ **`uses` は他人のコードを実行する**ということ。**素性を確かめる必要がある**（§6）。

### ⚠️ Secrets は「書き込み専用」

**CIに秘密を渡す仕組み。** ⚠️ **ただしAWSとは決定的に違う点がある。**

| | Parameter Store | GitHub Secrets |
|---|---|---|
| **読み出し** | ✅ **CLIでいつでも読める** | ❌ **一度入れたら二度と読めない** |
| **バックアップになるか** | ✅ なる | ⚠️ **ならない** |

⚠️ **だから「Secretsに入れたから安心」ではない。** **原本は別に保管する。**

📌 **ログに出そうとすると自動で `***` にマスクされる**（⚠️ **ただし base64 を展開して出せば漏れる**）。

## 5. ⚠️ 署名鍵をCIに置くかどうか

⚠️ **自動化で必ずぶつかる分岐。**

**①のビルドをCIでやるなら、⚠️ CIが署名しなければならない＝鍵をCIに渡すことになる。**

| | **CIでビルド・署名** | **手元でビルドし、AABだけ上げる** |
|---|---|---|
| **push だけで完結** | ✅ **する** | ❌ **しない**（手元作業が残る） |
| ⚠️ **鍵の置き場** | ⚠️ **CIにもコピーが存在する** | ✅ **手元だけ** |

⚠️ **鍵はバイナリなので、Secretsに入れるには base64 で文字列化する。**

### 📌 リスクの見積もり方

⚠️ **「漏れたら何が起きるか」で考える。**

- ⚠️ **第三者が「そのアプリの更新」として署名できる**ようになる
- 📌 **ただしストアに上げるにはサービスアカウントの鍵も要る**（二重の壁）
- ✅ **upload key なら再登録できる**（[14](14_android_app_signing_and_release.md) §3）

⚠️ **publicリポジトリでは特に注意。** 📌 **フォークからのPRでワークフローが走る設定にすると、
他人がSecretsに触れる経路ができうる。**

## 6. アップロードの手段（3通り）

⚠️ **どれを選んでも、§2のAPIを叩いている点は同じ。** **違いは「誰が書いたコードを使うか」。**

| | **既製のCLIツール** | **既製のCI部品（Action）** | **自分で書く** |
|---|---|---|---|
| **代表例** | **fastlane**（Ruby製・モバイル開発の定番） | `r0adkll/upload-google-play` 等 | Python/Node のスクリプト |
| **書く量** | ✅ **設定ファイルだけ** | ✅ **YAMLに数行** | ⚠️ **数十行** |
| **依存** | ⚠️ **Ruby環境が要る** | ⚠️ **他人のビルド済みコードを実行** | ✅ **公式ライブラリのみ** |
| **中身の把握** | ⚠️ 難しい | ⚠️ **難しい**（ビルド済みJSが実行される） | ✅ **完全に把握できる** |

> **AWSでいうと**: 📌 **AWS CLI を使うか / 誰かのCloudFormationテンプレートを使うか /
> boto3 で自分で書くか**、の三択に近い。

### ⚠️ 既製品を使うときの注意

⚠️ **`uses: someone/action@v1` のような可変タグは、あとから中身を差し替えられる。**

📌 **コミットSHAで固定すれば、その時点のコードに釘付けにできる:**

```yaml
- uses: someone/action@e738b9dd8f2476ea806d921b64aacd24f34515a5
```

⚠️ **個人が管理するリポジトリを使うなら、これは必須と考えてよい。**

## 7. 何をきっかけに走らせるか

| きっかけ | 評価 |
|---|---|
| **push すべて** | ⚠️ **ドキュメント修正でも配信が走る。** ⚠️ **バージョンが同じだとストアに弾かれ、失敗通知が常態化する** |
| ⚠️ **タグ（`v1.2.3` 等）** | ✅ **「バージョンを上げた」という意思表示と一致する**ので相性がよい |
| **手動実行** | 📌 **確実だが、押しに行く手間は残る** |
| **特定パスの変更を検知** | ⚠️ **CIによっては最新コミットしか見ない**ので、取りこぼす罠がある |

📌 **バージョン番号を上げないと、そもそもストアが受け付けない**（[14](14_android_app_signing_and_release.md) §5）。
⚠️ **つまり「配信してよいタイミング」は、バージョンを上げた瞬間と一致している。**

## 8. 📌 自動化する前に考えること

⚠️ **自動化は「速くなる」代わりに「持ち物が増える」。**

| 増えるもの | |
|---|---|
| ⚠️ **鍵の置き場** | 手元だけだったものが、CIにも増える |
| ⚠️ **壊れる箇所** | ⚠️ **CIの環境（SDK/JDKのバージョン）が手元とずれると、CIだけ失敗する** |
| **設定ファイル** | ワークフロー・サービスアカウント・権限 |

📌 **配る頻度が低いなら、手動のままでも十分**なことはある。
⚠️ **逆に「直して、すぐ配って、また試す」という往復があるなら、自動化の価値は大きい。**

📌 **判断の軸は「1回あたりの手間 × 回数」が「作る手間 + 抱えるリスク」を超えるか。**
