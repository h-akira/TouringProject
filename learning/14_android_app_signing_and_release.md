# 14. Androidアプリの署名とストアへの提出

**アプリを「自分の端末で動かす」から「他人に配る」へ進めるときに必要になる知識。**
配信手段の選び方は [13](13_private_app_distribution.md)、ここでは**選んだ後に何をするか**を扱う。

> **Webとの対応**: Webは**サーバに置けば配れる**が、⚠️ **Androidは「誰が作ったか」を
> 暗号署名で証明しないと配れない。** ここがWeb開発者にとって最大の段差になる。

## 1. 署名（signing）とは何か

**アプリのパッケージに、秘密鍵で電子署名を付ける仕組み。**

⚠️ **目的は「作者の証明」ではなく「同一性の証明」。**
Androidは**アプリの更新時に、前回と同じ鍵で署名されているか**を検証する。

| | |
|---|---|
| **署名が一致する** | ✅ **更新として上書きインストールできる**（データも設定も残る） |
| ⚠️ **署名が違う** | ❌ **インストールが拒否される**（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。**一度アンインストールするしかない＝データが消える** |

📌 **つまり署名鍵は「そのアプリを更新する権利」そのもの。**
⚠️ **鍵を失うと、利用者は更新を受け取れなくなる。**

### ⚠️ debug鍵という罠

**開発中は、ツールが自動生成する「debug鍵」で署名されている。**
⚠️ **これは全開発者で共通のパスワード（`android`）を持つ、公開された鍵。**

📌 **手元で動かすぶんには何の問題もない**が、⚠️ **ストアは受け付けない**
（誰でも同じ鍵で署名できるので、同一性の証明にならない）。

⚠️ **雛形の `build.gradle` は release も debug 鍵で署名する設定になっている**ことが多い。
**コメントで "In production, you need to generate your own keystore file." と
警告されているが、消し忘れやすい。**

## 2. キーストア（keystore）

**鍵を格納する、パスワードで暗号化されたファイル**（`.jks` / `.keystore`）。

```sh
keytool -genkeypair -v -storetype JKS \
  -keystore my-upload-key.jks \
  -alias upload -keyalg RSA -keysize 2048 -validity 10000
```

| 引数 | 意味 |
|---|---|
| `-alias` | ⚠️ **鍵の別名。** 1つのキーストアに複数の鍵を入れられるので、どれかを指す |
| `-validity` | ⚠️ **有効期間（単位は「日」）。** `10000` ≒ **27年** |
| `-keysize 2048` | RSA鍵の長さ |

### ⚠️ なぜ `-validity 10000` が定番なのか

⚠️ **期限が切れると、利用者が更新を受け取れなくなる。**

- **Android公式は「最低25年」を推奨**
- ⚠️ **Google Play は「有効期限が2033年10月22日より後」であることを要求**
- 📌 `10000日` ≒ 27年は**両方を満たす**（Android Studio の既定値でもある）

### ⚠️ SSH鍵とは守り方が違う

**Web開発者が引っかかりやすい点。**

| | SSH鍵 | キーストア |
|---|---|---|
| **守り方** | ⚠️ **ファイルのパーミッション**（`600`） | ⚠️ **パスワードで暗号化** |
| **空パスフレーズ** | ✅ **できる**（鍵は平文で保存され、OSが守る） | ❌ **できない**（⚠️ **6文字以上を要求される**） |

📌 **JKSは中身をパスワードで暗号化するので、パスワードが無いと成立しない。**

## 3. ⚠️ 鍵は2種類ある（Play App Signing）

**ここを理解しないと、鍵の管理方針を誤る。**

Google Play は **Play App Signing** という仕組みを使う（新規アプリでは必須）。

```
開発者                              Google Play                     利用者
  │                                     │                             │
  │ upload key で署名して提出 ────────▶ │                             │
  │                                     │ 検証して署名を付け替え        │
  │                                     │ ── app signing key で署名 ──▶│
```

| | **upload key** | **app signing key** |
|---|---|---|
| **持ち主** | **開発者** | ⚠️ **Googleが保管** |
| **役目** | **Googleに「投稿者が本人だ」と示す** | ⚠️ **利用者の端末が同一性を検証する本物の鍵** |
| **失ったら** | ✅ **再登録できる**（Play Console から申請。24〜48時間） | ❌ **回復不能** |

📌 **つまり「鍵を失うとアプリを二度と更新できない」は、
Play App Signing を使わない場合の話。**
⚠️ **使う限り、開発者が持つのは upload key だけ**なので、**最悪でも再登録で復旧できる。**

⚠️ **とはいえ再登録には日数がかかる**ので、失ってよいわけではない。

### 鍵の保管（一般的な3層）

| 層 | 何を置くか | 置き場 |
|---|---|---|
| **① 日常のビルド** | `.jks` の実体 | ⚠️ **リポジトリの外** |
| **② バックアップ** | `.jks` + パスワード | パスワード管理ツール／暗号化クラウド／外付けドライブ |
| **③ CI用** | `.jks` を base64 化したもの | CIのシークレット機構 |

⚠️ **①と③は別物。** **GitHub Secrets は書き込み専用で読み出せない**ので、
⚠️ **③はバックアップにならない。** 必ず②を別に持つ。

⚠️ **リポジトリには絶対に入れない。** **一度コミットすると履歴に永久に残る。**

## 4. APK と AAB

| | **APK** | **AAB**（Android App Bundle） |
|---|---|---|
| **正体** | ⚠️ **そのままインストールできる完成品** | ⚠️ **素材の詰め合わせ。インストールできない** |
| **誰が使う** | 手元での確認・直接配布 | ⚠️ **ストア提出用**（新規アプリはAAB必須） |
| **ABI** | 全部入り（＝重い）か、絞るか | 📌 **Playが端末ごとに必要なぶんだけ切り出して配る** |
| **コマンド** | `assembleRelease` | `bundleRelease` |

📌 **AABが大きく見えても、利用者のダウンロードサイズは増えない**
（⚠️ **Playが分割するため**）。

⚠️ **AABは実機に直接インストールできない。** 手元の確認にはAPKを使う。

### ⚠️ ABI（CPUアーキテクチャ）を絞ると配れなくなる

**ネイティブコードを含むアプリは、CPUごとに別のバイナリ（`.so`）を持つ。**

| ABI | 対象 |
|---|---|
| `arm64-v8a` | ⚠️ **現行のAndroid実機のほぼ全て** |
| `armeabi-v7a` | 古い32bit端末 |
| `x86` / `x86_64` | ⚠️ **主にエミュレータ** |

📌 **開発中は自分の実機のABIだけをビルドすると、ビルド生成物が劇的に減る**
（4種類ぶんの `.so` が作られなくなるため）。

⚠️ **しかし配布時に絞ると、そのABI以外の端末で動かない。**
⚠️ **配る相手の端末は選べない。**

📌 **AABなら全ABIを入れておけばPlayが振り分ける**ので、**配信用は全ABIにするのが正解。**

## 5. `versionCode` と `versionName`

⚠️ **別物。混同すると必ず詰まる。**

| | `versionCode` | `versionName` |
|---|---|---|
| **型** | ⚠️ **整数** | 文字列 |
| **例** | `10203` | `"1.2.3"` |
| **誰が見る** | ⚠️ **システムだけ** | 利用者 |
| **役割** | ⚠️ **新旧の判定**（大きい方が新しい） | 表示用 |

⚠️ **ストアは同じ `versionCode` を二度受け付けない。**
⚠️ **雛形は `versionCode 1` で固定されている**ので、**放置すると2回目のアップロードで弾かれる。**

### 📌 セマンティックバージョンから導出する

**人が管理する数字を1つに減らすと、上げ忘れが起きにくい。**

```
major * 10000 + minor * 100 + patch
1.2.3 → 1*10000 + 2*100 + 3 = 10203
```

⚠️ **各桁が99を超えられない**制約がつく点に注意。
⚠️ **単調増加すること**を確認する（`1.9.0` → `10900` < `1.10.0` → `11000` ✅）。

## 6. ⚠️ 秘密をビルド設定に書かない

**キーストアのパスワードをビルドスクリプトに直接書くと、2つ問題が起きる。**

| 問題 | 中身 |
|---|---|
| **平文で残る** | ⚠️ **生成物にパスワードがそのまま残る** |
| ⚠️ **消えない** | **生成ディレクトリは毎回作り直されるとは限らない**ので、**消したつもりで残る** |

📌 **ビルド時に環境変数から読ませるのが定石。**

```groovy
storeFile file(System.getenv('MY_KEYSTORE_PATH'))
storePassword System.getenv('MY_KEYSTORE_PASSWORD')
```

✅ **これなら生成物に秘密が一切残らない。**

### ⚠️ `.env` はシェルが読むわけではない

**ハマりやすい点。** `.env` を自動で読み込むのは**それを実装したツールだけ**で、
⚠️ **ビルドツール（Gradle等）を直接叩くと読まれない。**

📌 **明示的に読ませる:**

```sh
set -a && . ./.env && set +a && ./gradlew bundleRelease
```

⚠️ **ただしこれは shell の `source` であって dotenv パーサではない。**

| `.env` の書き方 | 結果 |
|---|---|
| `PASSWORD=abc def` | ⚠️ **`def: command not found`。変数は空** |
| `PASSWORD=abc#def` | ⚠️ **`#` 以降が捨てられる** |
| `PASSWORD='abc def#g'` | ✅ **正しく読まれる** |

⚠️ **パスワードは必ず引用符で囲む。** 囲まないと**変数が空のまま進み、
分かりにくいエラーになる。**

## 7. ⚠️ ストア提出は「アップロードすれば終わり」ではない

**実際に時間を食うのは、ファイルを上げた後の申告事項。**

```
アプリを作成 → ファイルをアップロード → ⚠️ 各種の宣言を埋める → 配布
                                        ↑ ここが本番
```

**よく求められるもの:**

| 宣言 | 中身 |
|---|---|
| **アプリのアクセス権** | ⚠️ **ログインやキーが必要なら、審査者が使える手順を書く** |
| **広告の有無** | |
| **コンテンツのレーティング** | アンケート形式 |
| **ターゲット層** | ⚠️ **子ども向けかどうかで要件が変わる** |
| **データセーフティ** | ⚠️ **何を集め、誰と共有するか** |
| **プライバシーポリシー** | ⚠️ **位置情報・マイク等を使うなら、ほぼ必須。URLで示す** |

⚠️ **「収集」と「共有」は別物。**
📌 **自分のサーバに送るのは「収集」**、**第三者に渡すのが「共有」**。
⚠️ **クラウドの処理委託先は、通常「共有」に当たらない。**

### ⚠️ 変更できないものに注意

| 項目 | |
|---|---|
| ⚠️ **パッケージ名**（`com.example.app`） | ❌ **変更不可。削除しても再利用できない** |
| ⚠️ **無料/有料** | ❌ **無料で公開すると有料にできない** |
| **アプリ名** | ✅ **変更できる**（⚠️ **反映に時間がかかることがある**） |

📌 **パッケージ名はドメインの逆順にする慣習**があるが、
⚠️ **ドメインを所有している必要はない**（一意でありさえすればよい）。

### 📌 自動化は初回の後から

⚠️ **ストアのAPIは「既に存在するアプリ」しか更新できない**のが一般的。
📌 **初回だけは画面から手でアップロードする必要がある**ので、
⚠️ **自動化を先に作っても使えない。**

## 8. 難読化（R8 / ProGuard）

**コードを縮小・難読化する仕組み。**

| | 有効にすると |
|---|---|
| ✅ | **アプリサイズが縮む・解析されにくくなる** |
| ⚠️ | **クラッシュログが読めなくなる**（マッピングファイルで復元する） |
| ⚠️ | **リフレクションで参照されるクラスが消えて実行時エラーになりうる** |

📌 **既定は無効**なことが多い。⚠️ **無効なら「マッピングファイルが無い」という
警告が出るが、それは正常**（難読化していないので、そもそも生成されない）。
