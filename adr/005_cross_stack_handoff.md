# 005. スタック間の受け渡しをSSMにし、パイプラインは暫定で1本にする

- **日付**: 2026-08-15
- **ステータス**: 採用（一部改訂）
- **現在の設計**: [docs/01](../docs/01_architecture.md) §10・§11

## 背景

デプロイを自動化するにあたり、**`Agent/`（CDK・us-east-1）と `Backend/`（SAM・東京）は
別スタックで、後者が前者の Runtime ARN を必要とする**という制約がある。
手作業のときは `list-agent-runtimes` で引いて渡していた。

自動化すると、**この受け渡しをどこかに固定する必要がある**。

## 選択肢1: Runtime ARN をどう渡すか

### 案A: SSMパラメータ（採用）

Agentのデプロイ後に `/trg/<env>/agent-runtime-arn` へ書き、
BackendのSAMが `AWS::SSM::Parameter::Value<String>` で読む。

### 案B: CloudFormationのエクスポート / `Fn::ImportValue`

⚠️ **技術的に不可能。** AgentCoreのスタックは Runtime ARN を
**エクスポートしている**（`...-RuntimeArn`）が、それは **us-east-1** にある。
Backendは**東京**で、**`Fn::ImportValue` はリージョンを跨げない**
（東京側のエクスポート一覧が空であることを確認した）。

**本来これが最も素直**なので、⚠️ **リージョンを揃えられた場合は再検討の価値がある**
（条件はWeb検索コネクタが東京に来ること。[docs/01](../docs/01_architecture.md) §6）。

### 案C: CI/CDスタックのパラメータとして渡す

**却下。** Agentを作り直すとARNが変わり、**そのたびにCI/CDスタックの再デプロイ**が要る。
「デプロイを自動化する」目的に対して手作業を増やす。

## 選択肢2: パイプラインを分けるか

### 案A: 1本にまとめる（採用・⚠️ 暫定）

**いまは技術検証をしながら進めており、`Agent/` と `Backend/` を
同時に触ることが多い。** 同じリポジトリにある以上、1本の方が
**順序が自明**で、受け渡しも同一ビルド内で完結する。

### 案B: 最初から2本に分ける

**却下（ただし将来やる）。** いま分けると、
**Agentの完了を待ってBackendを起こす仕組み**が別途要る。
検証段階でその複雑さを抱える利点が無い。

## 決定

**Runtime ARN は SSM 経由で渡し、CodeBuild は暫定で1本**にする
（`Agent → SSM → Backend` の順）。

### ⚠️ 1本なのは暫定であり、分ける前提で作る

**将来 `Agent/` と `Backend/` は別リポジトリ・別パイプラインになりうる。**
そのとき困らないよう、いまの時点で以下を満たしておく:

- **受け渡しは既にSSM経由**なので、分けても**そのまま動く**
  （ビルド内の変数で渡していたら、分ける時点で作り直しになる）。
- **`buildspec.yml` はリポジトリ直下**に置く。CodeBuildが既定で見る場所であり、
  **分割後は各リポジトリの直下**になる。`CICD/` に置くのは
  「CodeBuild自体を作るCloudFormation」だけ。

→ **分けるときにやるのは「Agentの後にBackendを走らせる」順序の担保だけ**で、
受け渡しの再設計は要らない。

### ⚠️ パスフィルタは使わない

`FILE_PATH` フィルタは**pushのheadコミットしか見ない**ため、
最後のコミットがドキュメントだけだと**同じpushに含まれる `Backend/` の変更ごと
静かにスキップ**される（実際に起きた。Webhookの配信は `200 OK`）。

**空振りのビルドは安く**（CloudFormationもSAMも変更が無ければ何もしない）、
**静かに実行されないデプロイは高い**ので、`main` へのpushは常にビルドする。

## 影響

- ⚠️ **Agentを先にデプロイしていないとBackendが失敗する**
  （`Parameter /trg/... not found`）。これは仕様どおりの挙動。
- **`sam deploy` が引数なしで通るようになった。**
  渡すのは**SSMパラメータ名**でアカウントIDを含まないため、`samconfig.toml` に置ける。
  📌 手元では changeset の確認プロンプトが出る（CIは `--no-confirm-changeset`）。
- ⚠️ **`--parameter-overrides` はsamconfigの指定を「併合せず置き換える」**（実測で確認）。
  一部だけ変えるつもりで省くと、テンプレートの既定値に戻る。
- **CodeBuildのIAMロールは広め。** SAMとCDKが2スタックぶんのリソースを作るため。
  ⚠️ **CodeBuildからしか使えず、実行するのはこのリポジトリのbuildspecだけ**という前提で許容している。
- **`App/` はCI/CDの対象外。** Expo経由で配布するのでAWSにデプロイするものが無い。

## 改訂（2026-09-25）: パイプラインを2本に分けた

**「選択肢2」の暫定（1本にまとめる）を終えた。** リポジトリを分離し（[adr/011](011_repository_split.md)）、
**CodeBuild を Agent 用・Backend 用の2つにした。** **選択肢1（SSMでの受け渡し）はそのまま生きている。**

- 案Bの却下理由だった「**Agentの完了を待ってBackendを起こす仕組み**」は、
  **ARN が変わったときだけ Agent のビルドが Backend のビルドを起動する**形で入れた。
- ⚠️ **ここで想定していなかったこと**: 「分けるときにやるのは順序の担保だけ」は、
  **初回だけを見ていた。** Backend は ARN を**デプロイ時に焼き込む**ので、
  **ランタイム名の変更後は、Backend を再デプロイしない限り古いランタイムを呼び続ける**
  （「影響」の「Backendが失敗する」は初回にしか当たらない）。これが上の起動を入れた理由。
