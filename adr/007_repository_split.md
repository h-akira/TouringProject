# 007. Agent・Backend・App・CICD を別リポジトリに分け、親から submodule で束ねる

- **日付**: 2026-09-25（最終更新 2026-09-27）
- **ステータス**: 採用

## 背景

1つのリポジトリに `Agent/` `Backend/` `App/` `CICD/` が同居し、デプロイの設定が1つに絡んでいた。
App の Play 配信を自動化すると、どの変更で何が動くかがさらに絡む。
Agent と Backend のデプロイ方法は確立済みで、受け渡しも SSM 経由（[006](006_cross_stack_handoff.md)）なので、分けても再設計は要らない状態だった。

## 選択肢

| 案 | 判断 |
|---|---|
| A. 1リポジトリのまま、変更されたパスで動かし分ける | 却下。何が動くかがフィルタの正しさに依存する。構成そのもので決まる方が単純 |
| B. 完全に分け、親を無くす | 却下。ユニットを跨ぐ成果物（要件・共通の設計・契約・ADR）の置き場が無くなる |
| **C. 分け、親から submodule で束ねる** | 採用。同じ開発者の別プロジェクトで同じ構成の運用実績がある |
| D. subtree | 却下。親に中身が複製され、双方向の同期が重い |

### 公開の範囲

| 案 | 判断 |
|---|---|
| 4リポジトリとも public | 却下。CICD は Bedrock を呼ぶ AWS 側のデプロイの仕組みそのもので、不正利用されたときの被害が大きい。公開しても得るものが無い |
| **CICD だけ private** | 採用 |

## 決定

- `TouringProject_Agent` / `_Backend` / `_App`（public）と `_CICD`（private）を作り、親の同じ場所に submodule として置く。
- git の履歴は引き継がない（分離前の履歴は親にある）。
- 公開側（README・docs・adr）では、CI/CD があること・CodeBuild を使うこと・CICD へのリンクまでは書くが、構成・権限・順序の仕組みは書かない。対象は Bedrock を呼ぶ AWS 側（Agent・Backend）だけで、App の Play 配信（GitHub Actions）は対象外。
- App が API の契約を必要とするので、親の `docs/` の写しを各ユニットに `docs-parent/` として置く（写し方は [008](008_docs_per_unit.md)）。App は単体でクローンしても型を生成できる。

## 影響

- ⚠️ Agent と Backend のデプロイが別々になる。Backend は ARN をデプロイ時に焼き込むので、ARN が変わったら Backend も再デプロイする。
- Agent と Backend に跨る変更は、2つのデプロイの間だけ食い違う（dev しか無いので許容する）。
- サブを変えるたびに、親でポインタを更新するコミットが要る。親のポインタはデプロイと無関係なので、忘れても壊れはしないが古くなる。
- ⚠️ push はサブ → 親の順。逆だと親が存在しないコミットを指す。
- サブから親へのリンク、親からサブへのリンクは絶対 URL にする（GitHub 上で単体表示しても切れないように）。
- CICD へのリンクは他の人には切れて見えるが、許容する。
- App のタグ（`v<version>`）は App リポジトリに打つ。分離前のタグは親に残る。
