# 001. 回答の受け取りを非同期にする

- **日付**: 2026-08-13
- **ステータス**: 採用
- **現在の設計**: [docs/01a_async_ask.md](../docs/01a_async_ask.md)

## 背景

**API Gateway は1リクエスト29秒で必ず切れる**（引き上げ不可）。
一方エージェントの生成は遅く、実測でこうなっていた:

| | 生成完了まで |
|---|---|
| 初回（コールドスタート込み） | 12.5秒 |
| 2回目以降（ウォーム） | **10.2秒** |
| 最悪ケース（トークン上限まで生成） | **25.5秒** |

余裕は3.5秒。しかも**コールドスタートを除いても毎回10秒使っている**。
次にやる音声化（US-2.01/02）でSTT/TTSが乗れば、確実に超える。

⚠️ 「たまに失敗する」状態が一番厄介だと判断した。29秒はギリギリ足りていたので、
放置すれば「長い回答のときだけ落ちる」という再現しにくい不具合になっていた。

## 選択肢

### 案A: 非同期ポーリング（採用）

`POST /ask` は即座に `requestId` を返し、アプリが `GET /ask/{requestId}` で取りに行く。
エージェントの呼び出しは別Lambdaで行う。

### 案B: WebSocket

API Gateway WebSocket で結果をプッシュする。

**却下。** 制約は外れるが接続管理が増える。逐次配信できる利点も、
**音声で読み上げる以上は文章が完成しないと喋り出せない**ため、
現在の音声方式（手前でSTT・後でTTS）では活きない。

### 案C: Lambdaを外してアプリからAgentCoreを直接叩く

**却下。** 29秒制約そのものが消えるが、認証（Cognito）と
住所解決の置き場所を巻き込む再設計になる。いま決めるには影響が大きすぎる。

### 案D: 据え置き（回答を短くして時間を削る）

**却下。** 延命にしかならない。生成が10秒かかる事実は変わらない。

## 決定

**案A（非同期ポーリング）を採る。** 既存構成をほぼ保てるのが決め手。
案Cは将来の選択肢として残るが、音声化を優先する。

### worker の起動は SQS 経由にする

Lambda から Lambda を直接呼ばず、キューを挟む一般的な作法に従う。

> ⚠️ **検討の過程で誤った理由づけをした。**
> 当初「利用者が1人だからSQSは過剰」と述べたが、これは**今だけの話で根拠にならない**。
> 公式ドキュメントを確認した結果、判断材料は以下だった:
>
> - Lambda の非同期呼び出し（`InvocationType='Event'`）にも
>   [AWS内部のキューがある](https://docs.aws.amazon.com/lambda/latest/dg/invocation-async.html)。
>   直呼びではない。
> - ただし**そのキューは自分のものではない**ので、滞留の可視化や制御ができない。
>
> → 可視性の高いSQSを採る。

### ⚠️ 冪等性を必ず入れる

SQSは**少なくとも1回**の配信で、
[AWS公式](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html) が
"we strongly recommend that you make your function code idempotent" と警告している。

**このアプリでは二重処理＝AgentCoreの二重呼び出し＝二重課金**になるため、実害がある。
対策は2層（時間の大小関係＋条件付き書き込み）。詳細は
[docs/01a](../docs/01a_async_ask.md) §5。

### FIFOキューは使わない

「FIFOの重複排除で防げるのでは」を検討したが、**今回の重複には効かない**。
重複排除が効くのは「同じメッセージを2回**送信**したとき」で、
今回懸念しているのは**可視性タイムアウト切れによる再配信**。メッセージは1回しか送っていない。

加えて FIFO は同一グループを直列処理するため、順序保証の利点も活きない。

## 影響

- **APIの契約が変わる**（`POST /ask` は 200+回答 → **202+requestId**）。
  `GET /ask/{requestId}` を追加。
- **AWSリソースが増える**（SQS・DLQ・DynamoDB・Lambda2つ）。
- ⚠️ **アプリはポーリングを必ず止める責任を負う**（80秒で打ち切り、画面離脱で停止）。
- ⚠️ **worker Timeout(120秒) < 可視性タイムアウト(180秒)** の関係を崩せない。
- **待ち時間そのものは縮まらない。** タイムアウトしなくなるだけで、
  体感を縮めるには別の施策（回答を短くする等）が要る。
