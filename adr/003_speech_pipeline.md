# 003. 音声は手前で文字にし、STT/TTS は Lambda が呼ぶ

- **日付**: 2026-08-12（最終更新 2026-09-27）
- **ステータス**: 採用

## 背景

走行中は画面を見られないので、入出力は音声である必要がある（US-2.01/2.02）。
どこで STT/TTS を行うかで構成が大きく変わる。

## 選択肢

### 音声の扱い方

| 案 | 判断 |
|---|---|
| **A. 手前で STT、後で TTS**（エージェントにはテキストを渡す） | 採用。既存のエージェントを変えずに済み、実装が最も軽い |
| B. 音声を双方向でやり取りする（WebSocket） | 却下。接続管理が増え、Lambda を中継役（門番）として使えなくなる |
| C. Nova 2 Sonic（音声→音声の基盤モデル） | 却下。日本語に対応していない（音声の一覧に `ja-JP` が無い）。STT/TTS を挟まないので最も自然で遅延も小さい |

### STT をどこで呼ぶか

Transcribe にはストリーミング（`StartStreamTranscription`、双方向で Lambda を経由できない）とバッチ（`StartTranscriptionJob`、S3 に置いた音声を処理する）がある。

| 案 | 判断 |
|---|---|
| D. アプリが Transcribe（ストリーミング）を呼び、API にはテキストを送る | 却下。アプリに AWS の認証情報が要る。音声が Lambda に届かないので録音の長さを手前で検証できず、アプリを改造されると Transcribe の秒課金が無防備になる。喋りながら認識する必要は本アプリに無い |
| **E. アプリは音声ファイルを API に送り、Lambda が Transcribe（バッチ）と Polly を呼ぶ** | 採用 |

## 決定

- アプリは録音した音声を `POST /ask-audio` に送る。テキストの `POST /ask` はそのまま残す。
- Lambda が音声を S3 に置いて Transcribe のバッチを投げ、完了（EventBridge）を受けてから住所・方位を確定し、テキストと同じ非同期の経路（[004](004_async_ask.md)）に合流させる。
- 回答の音声は Polly で作って S3 に置き、アプリには署名付き URL を渡す。

門番としての Lambda が音声にも効く。ペイロードのサイズ（＝録音の長さ）を手前で弾け、アプリは API キーだけで完結する（[005](005_api_key_auth.md)）。

## 影響

- バッチにはジョブのキューイングがあり、所要時間が保証されない（同時実行の上限に達したときの話で、単一の利用者では出ない見込み）。
- STT のぶん応答が遅くなる（テキスト10〜13秒に対し、音声は15〜20秒）。
- Transcribe が文字起こしを自分のバケットに書くための IAM ロールが要る。
- ⚠️ Nova 2 Sonic が日本語に対応したら、案C を再検討する。
