# 004. 回答を非同期で受け取る（SQS ＋ DynamoDB ＋ ポーリング）

- **日付**: 2026-08-13（最終更新 2026-09-27）
- **ステータス**: 採用

## 背景

API Gateway は1リクエストを29秒で必ず切る（引き上げ不可）。一方、エージェントの生成は遅い。

| | 生成完了まで（実測） |
|---|---|
| 初回（コールドスタート込み） | 12.5秒 |
| 2回目以降 | 10.2秒 |
| 最悪（トークン上限まで生成） | 25.5秒 |

余裕は3.5秒しかなく、音声化（STT/TTS）が乗れば確実に超える。
29秒にぎりぎり収まる状態を放置すると「長い回答のときだけ落ちる」再現しにくい不具合になる。

## 選択肢

| 案 | 判断 |
|---|---|
| **A. 非同期ポーリング** | 採用。`POST /ask` は即座に `requestId` を返し、アプリが `GET /ask/{requestId}` で取りに行く。既存の構成をほぼ保てる |
| B. WebSocket で結果を送る | 却下。接続管理が増える。逐次配信の利点も、読み上げは文章が完成しないと始められないので活きない |
| C. Lambda を外し、アプリから AgentCore を直接呼ぶ | 却下。認証（Cognito）と事実の確定の置き場所を巻き込む再設計になる（[002](002_agentcore_as_orchestrator.md)） |
| D. 回答を短くして時間を削る | 却下。延命にしかならない |

### worker の起動方法

| 案 | 判断 |
|---|---|
| **SQS を挟む** | 採用。滞留を自分のキューとして見られ、DLQ も持てる |
| Lambda の非同期呼び出し（`InvocationType='Event'`） | 却下。AWS 内部にキューはあるが自分のものではなく、滞留の可視化や制御ができない |
| FIFO キュー | 却下。重複排除が効くのは同じメッセージを2回送信したときで、懸念している可視性タイムアウト切れの再配信には効かない。順序保証の利点も無い |

## 決定

案A を採る。`POST /ask`（テキスト）と `POST /ask-audio`（音声）は 202 と `requestId` を返し、worker Lambda が SQS から受けて AgentCore を呼び、結果を DynamoDB に置く。アプリは `GET /ask/{requestId}` をポーリングする。

⚠️ SQS は「少なくとも1回」配信するので、二重処理は AgentCore の二重課金になる。対策は2層にする。

1. 時間の大小関係: worker の Timeout（120秒）＜ 可視性タイムアウト（180秒）
2. 条件付き書き込み: worker は `pending → processing` を条件付きで行い、2つ目の worker は獲得に失敗して AgentCore を呼ばずに終わる

## 影響

- API の契約が変わった（`POST /ask` は 202＋`requestId`）。ポーリングの間隔と打ち切りは契約として定める（[docs/03_units_contracts.md](../docs/03_units_contracts.md)）。
- AWS のリソースが増える（SQS・DLQ・DynamoDB・Lambda 2つ）。
- ⚠️ アプリはポーリングを必ず止める責任を負う（打ち切り時間・画面を離れたとき）。
- ⚠️ worker の Timeout を伸ばすときは可視性タイムアウトも伸ばす。
- 待ち時間そのものは縮まらない。タイムアウトしなくなるだけ。
