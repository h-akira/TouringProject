# 003. 会話の司令塔を AgentCore にする（Lexは使わない）

- **日付**: 2026-07-30
- **ステータス**: 採用
- **現在の設計**: [docs/01_architecture.md](../docs/01_architecture.md) §3
- **検証**: [pre-research/agentcore/](../pre-research/agentcore/)

> 📌 決定自体は 2026-07-30。ADRとして書き起こしたのは 2026-08-13。

## 背景

当初の構想では **Lambda が司令塔**で、STT → LLM → TTS を順に呼ぶ設計だった。

しかし「**続けて質問できる**」ことを要件に加えた（US-1.02）ことで、
会話の履歴を誰が持つのかという問題が生じた。
Bedrock の Converse API は**ステートレス**で、`sessionId` 相当のパラメータを持たない（実測確認済み）。

## 選択肢

### A. Lambda が履歴を管理する

毎回すべての履歴を Converse API に送り直す。**却下** — 自前で持つ必要があり、
保存先（DynamoDB等）と切り詰めのロジックを実装することになる。

### B. Bedrock Agents (Classic)

**却下。⚠️ 2026-07-30 で新規受付終了**のため、そもそも採用できない。

### C. AgentCore（採用）

セッション管理がネイティブ。`runtimeSessionId` を渡せば文脈が繋がる。

### Amazon Lex を挟むか

**却下。** 「音声＝Lex」と考えがちだが、
**Lex は"定型的なチャットボット"用**の意図理解エンジンで、
「ピザを注文」→注文フローに分岐、のような**あらかじめ決めた意図に振り分ける**用途に向く。

本アプリがやりたいのは「**自由な質問にLLMが自由に答える**」こと。
意図理解は **LLM自身が行う**ため、間にLexを挟むと二重になり、対話の自由度をむしろ制約する。

## 決定

**AgentCore を司令塔にし、Lambda は門番に徹する。** Lexは使わない。

### Lambda を残す理由

AgentCore は**それ自体がエンドポイントを持つ**ため、アプリから直接呼ぶこともできる
（Cognito + JWT。実現可能性は確認済み）。それでも Lambda を挟むのは:

- **流量制限**は API Gateway の Usage Plan に依存しており、AgentCore に同等の機能が見当たらない
- **入力量の上限**を、Bedrockを呼ぶ前に手前で弾ける
- **LLMに渡す前に事実を確定させる場所**として要る（住所・方位。[docs/01](../docs/01_architecture.md) §4）
- **後から外すのは容易だが、外した後で足すのは再設計**になる

### AgentCore Memory は使わない

セッションを越えた永続記憶の機能があるが、**採用しない**。
要件は「一問一答＋α」までで、**15分以上あけて前の会話の続きを求める使い方は想定しない**。

将来「走行ログを残す」等が出たら、それは**会話の記憶ではなくDB連携**として別に設計する。

## 影響

- **リージョンが分かれる。** Web検索コネクタが us-east-1 限定のため、
  `touringAgent/` は us-east-1、`backend/` は東京になる（[docs/01](../docs/01_architecture.md) §6）。
- **IaCが2つ並存する。** `agentcore` CLI が生成するのはCDKで、`backend/` はSAM。
- ⚠️ **アイドル中も課金される。** 文脈保持のため microVM が生存する。
  ツーリングは散発的な質問になるので、**コスト影響は要実測**。
- **将来の拡張は `@tool` を足す形**で行える。メモ機能（US-X.01）を見据えた構造。
