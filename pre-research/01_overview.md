# ツーリングAI会話アプリ 構想概要

## 1. 目的

バイクでのツーリング中に、**現在地の状況に基づいてAIと音声で対話できる**アプリを作る。
走行中は手が使えないため、イヤモニ（Bluetoothイヤホン）を通じた音声入出力を前提とする。

## 2. 背景・モチベーション

ツーリング中には、その場・その瞬間にしか湧かない疑問が多い。

- 「右手に見えるあの山は何？」
- 「この地域の特色は？」
- 「この先に立ち寄れそうな名所はある？」

これらは**現在地・進行方向という文脈**があって初めて成立する質問であり、
停車してスマホを操作していては体験が途切れてしまう。走りながら気軽に問いたい。

## 3. 想定する利用シーン

- ライダーはヘルメットを被り、Bluetoothイヤホン（インカム）を装着している
- スマートフォンはハンドル等のホルダーに固定、または収納したまま
- **手・視線を運転から離せない**（画面タップ・注視は不可）
- 走行中（＝端末が移動し続けている）が主なシーン

## 4. コア機能（MVP）

1. **現在地の取得** — GPSで緯度経度を取得
2. **進行方向の取得** — 走行中の位置変化（2点間）から進行方位を算出
3. **音声入力（STT）** — ライダーの発話をテキスト化
4. **AIによる応答生成** — 現在地・進行方向を文脈として与え、質問に回答
5. **音声出力（TTS）** — 回答を音声で読み上げ、イヤホンへ

### 「右手に見える山は何？」を成立させる仕組み

- 現在地（緯度経度）＋進行方位（北を0°とした角度）が分かれば、
  「右手＝進行方向から時計回りに90°の方向」を地理的に特定できる。
- その方向にある地物（山・湖・施設など）を地図データやAIの知識から回答する。

## 5. 操作方法に関する論点（最重要）

走行中は画面操作もヘルメット内ボタン操作も現実的でない。加えて、
**ナビアプリを前面に出して走るため、本アプリは常にバックグラウンドで動く必要がある。**
そのため操作方式は、**「アレクサ」のようにウェイクワードで呼びかけると起動する完全ハンズフリーが必須要件**（妥協不可）。

- 例:「ねえ、○○」→ AIが聞き取りモードに入る → 質問 → 音声で回答
- この「バックグラウンドで常時マイクを聴き続けてウェイクワードを検知する」方式が必須であることから、
  **Webアプリ（PWA）は却下となり、ネイティブ相当での実装を前提とする。**
- 詳細な検討（フレームワーク・ウェイクワードエンジンの比較）は [技術選定ドキュメント](./02_tech_selection.md) にて行う。

## 6. 前提・スコープ

| 項目 | 内容 |
|---|---|
| 対象プラットフォーム | まずは自分のAndroid端末のみ（審査・一般配布は当面考えない） |
| 実装形態 | **React Native に確定**（既存Web開発知識の活用を最重視。Web(PWA)は却下）。唯一のリスク＝バックグラウンド音声はPoCで検証し、破綻時はKotlinネイティブへ再検討 |
| 方向の取得方式 | GPSの2点間から進行方位を算出（磁気コンパスは補助的に検討） |
| ウェイクワード | Picovoice Porcupine を第一候補（個人利用は無料枠内） |
| バックエンド | AWS Lambda 経由で Amazon Bedrock を呼び出す想定。STTはTranscribe、TTSはPollyを想定 |
| 開発者のスキル | AWS・Vue・Lambda の知見は十分。Androidネイティブの知見はなし |

## 7. 非機能・懸念事項

- **安全性**: 運転への集中を削がないこと。応答は簡潔に。長時間の注視を誘発しない。
- **画面ロック中の継続動作**: 走行中は画面を触らないため、ロック／スリープ中でも動作し続ける必要がある。
- **通信・バッテリー**: 常時マイクON・常時通信はバッテリーと通信量を消費する。
- **騒音環境**: 走行風・エンジン音の中での音声認識精度。
