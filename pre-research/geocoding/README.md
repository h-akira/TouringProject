# 逆ジオコーディング（座標→住所）の検証

> 実施日: 2026-08-12 / 前提: [../../docs/00_user_stories.md](../../docs/00_user_stories.md) US-1.01（現在地を踏まえた回答）
>
> **問い**: 緯度・経度をLLMにそのまま渡して住所を判断させてよいか。
>
> 📌 逆ジオコーディング**そのものの基礎知識**（他プロジェクトでも通用する話）は
> [../../learning/61_reverse_geocoding.md](../../learning/61_reverse_geocoding.md) にある。
> こちらは**このアプリでどれを選んだか**の判断記録。

## 結論（先に要点）

**LLMに座標を解釈させるのは不可（実機で約40km離れた市を答えた）。逆ジオコーディングの専用APIを挟む。**

**採用: Amazon Location Service の `geo-places` reverse-geocode。**

| 案 | 精度 | レイテンシ | 費用 | 判定 |
|---|---|---|---|---|
| **LLMに座標を渡す**（現状） | ❌ **約40kmずれた** | 0（追加なし） | 0 | ❌ **不可** |
| **Amazon Location `geo-places`** | ✅ 正確・**構造化データ** | **約110〜160 ms** | 従量 | ✅ **採用** |
| 国土地理院（GSI）API | ✅ 正確 | 60〜230 ms | **無料** | 次善（§4） |

## 1. 何が起きたか（実機で発覚）

**実機で試したところ、隣県の別の市を現在地として答えた。** 直線で約40km離れている。

CloudWatch Logs で確認したところ、**座標は正しくLambdaからエージェントへ届いていた**。
それにもかかわらず、**エージェントは誤った市名でWeb検索していた**（検索クエリのログから確認）。

→ **配線は正常。LLMが座標を住所に変換する段階で間違えている。**

正解は公的なAPI2つ（国土地理院・Amazon Location）で裏を取り、**どちらも一致**した。
**LLMは緯度を約0.35度（≒40km）ずらして解釈していた。**

> 📌 **これは「プロンプトを工夫すれば直る」類の問題ではない。**
> LLMは座標と地名の対応を数値として厳密に保持しているわけではないので、
> **緯度経度の逆変換は原理的に苦手**（もっともらしい近隣の地名を出してしまう）。
> ツーリングでは「今いる場所」が回答の土台なので、**ここがずれると回答全体がずれる。**

> ⚠️ **この検証では実際の現在地の座標を記録しない**（個人の居場所は公開情報にしない）。
> 以下の実測は、東京駅など**公共のランドマーク**の座標で再現したもの。

## 2. 採用案: Amazon Location Service（`geo-places`）

```python
import boto3
c = boto3.client("geo-places", region_name="ap-northeast-1")
r = c.reverse_geocode(QueryPosition=[lon, lat], MaxResults=1)  # 経度が先
addr = r["ResultItems"][0]["Address"]
addr["Region"]["Name"]  # 東京都
addr["Locality"]        # 千代田区
```

### 実測（boto3・接続ウォーム後、ap-northeast-1）

| 地点 | AWS の結果 | レイテンシ |
|---|---|---|
| 東京駅 | 東京都 / 千代田区 | 156 ms |
| 箱根付近（35.0, 139.0） | 静岡県 / 伊豆市 | 118〜198 ms |
| 徳島の山中（34.0658, 134.0） | 徳島県 / 美馬市 | 109〜149 ms |
| 札幌（43.06, 141.35） | 北海道 / 札幌市 | 157 ms |
| 房総沖（35.0, 141.5・海上） | **(no result)** | 152 ms |

**約110〜160 ms。** 現状の応答時間（初回18.9秒 / 2回目以降3秒）に対して無視できる。

### 採用理由

- ✅ **`Region`（県）と `Locality`（市）が構造化されて返る** — プロンプトに埋めるのが容易。
  GSIは市区町村コードなので、コード→名称の対応表を自前で持つ必要がある（§4）
- ✅ **インデックスの事前作成が不要**（旧 `location` APIの `PlaceIndex` は要作成だった）
- ✅ AWS内で完結（外部APIキー不要・IAMで権限管理）
- ✅ 既存の権限で**すでに呼べた**（追加設定なしで実測できた）

### ⚠️ 注意点

- **引数は経度→緯度の順**（`QueryPosition=[lon, lat]`）。逆に渡すと違う場所になる
- **海上・国外ではヒットしない**（`ResultItems` が空。実測で確認）。
  海沿いを走る場面はあるので、**空のときは座標だけを渡してLLMに任せるフォールバックが必要**
- 返る `Label` は**詳細すぎる**（実測では店舗名やトイレの名前まで入った）。
  **`Region` + `Locality` を使い、`Label` はそのまま読み上げない**
- ⚠️ **`Label` には番地まで含まれる。** ログや将来のメモ機能で**そのまま保存しないこと**
  （現在地は個人情報。docs/01 の設計に照らして扱いを決める）

## 3. どこに挟むか

**Lambda（`Backend/src/handlers/ask.py`）で座標→住所に変換し、住所をエージェントに渡す。**

```
アプリ（座標） → Lambda〔逆ジオコーディング〕→ エージェント（住所＋座標）
```

理由:

- Lambdaは既に**入口の門番**という役割（[../agentcore/AUTH.md](../agentcore/AUTH.md)）。
  「LLMに渡す前に事実を整える」のはその役割に収まる
- エージェント側に置くと `@tool` になり、**LLMが呼ぶかどうかを判断してしまう**。
  現在地は毎回必要な前提情報なので、**判断させずに必ず付ける方が確実**
- ⚠️ リージョン: Lambdaは東京で、`geo-places` も**東京で呼べる**（実測済み）。
  エージェント（us-east-1）側に置く場合と違い、**リージョン跨ぎが増えない**

> 📌 **これは「Lambdaを挟む」判断の追加根拠になる。**
> [../agentcore/AUTH.md](../agentcore/AUTH.md) では「後から外せるから当面残す」という消極的な理由だったが、
> **LLMに渡す前に事実を確定させる場所**という積極的な役割が見つかった。

## 4. 次善案: 国土地理院（GSI）API

無料・APIキー不要で精度も十分。**採用しなかったのは扱いにくさのため。**

```
GET https://mreversegeocoder.gsi.go.jp/reverse-geocoder/LonLatToAddress?lat=35.6812&lon=139.7671
-> {"results":{"muniCd":"13101","lv01Nm":"丸の内一丁目"}}   # 東京駅
```

| 項目 | 内容 |
|---|---|
| 精度 | ✅ 正確（東京・箱根・徳島・札幌で確認。AWSと一致） |
| レイテンシ | ✅ 60〜230 ms（速いが振れ幅がある） |
| 費用 | ✅ **無料** |
| ⚠️ 出力 | **市区町村コード**（`13101`）。県名・市名の文字列が返らない |
| ⚠️ 依存 | 外部（AWS外）への通信。SLAなし・利用規約の確認が必要 |
| ⚠️ 範囲 | 日本国内のみ（海上はエラー） |

**`muniCd` → 「東京都千代田区」の対応表（約1900件）を自前で持つ必要がある**のが決め手で見送った。
Amazon Location のコストが問題になった場合は、ここに切り替える余地がある。

## 5. ⭐ Amazon Location は住所だけではない —「あの山は？」に使える

**住所変換（`ReverseGeocode`）以外にも周辺検索のAPIがあり、`natural_and_geographical`
カテゴリで山を距離付きで列挙できる。** これは US-1.01「右手に見える山は何？」の直接の解になる。

### 利用できる操作

| サービス | 操作 |
|---|---|
| `geo-places` | `ReverseGeocode` / `SearchNearby` / `SearchText` / `Geocode` / `GetPlace` / `Autocomplete` / `Suggest` |
| `geo-routes` | `CalculateRoutes` / `SnapToRoads` / `CalculateIsolines` / `CalculateRouteMatrix` / `OptimizeWaypoints` |
| `geo-maps` | `GetStaticMap` / `GetTile` 等（地図画像。走行中は使わない） |

### 実測: 周辺の山を列挙する

```python
r = c.search_nearby(
    QueryPosition=[lon, lat],
    QueryRadius=15000,                                   # メートル
    Filter={"IncludeCategories": ["natural_and_geographical"]},
    MaxResults=10,
)
```

箱根付近（35.2323, 139.0230）で **207 ms・10件**:

| 地点 | 距離 |
|---|---|
| 早雲山 | 1957 m |
| 金時山 | 2423 m |
| 箱根山 / 神山 | 3029 m |
| 大観山 | 5881 m |
| 丸岳 | 7622 m |

⚠️ **カテゴリはID指定**（`natural_and_geographical`）。表示名 `Natural and Geographical` を
渡すと `ValidationException` になる。IDは検索結果の `Categories[].Id` から確認できる。

### 方角も出せる（`Position` が返るため）

各結果に `Position`（経度・緯度）が入るので、**現在地からの方位は自前で計算できる**。
上と同じ地点で計算した結果:

| 山 | 方角 | 距離 |
|---|---|---|
| 早雲山 | 北東 | 1957 m |
| 金時山 | 北西 | 2423 m |
| 神山 | 南南東 | 3029 m |
| 浅間山（箱根町） | 東 | 4548 m |

→ **進行方位（US-2.03）と組み合わせれば「右手に見える山」を特定できる。**
「進行方向が北で、山が北東にあるなら右手」という判定が、**LLMの推測ではなく計算で**成立する。

### 将来: AIに `@tool` として持たせる案

**現在地の住所変換（§3）はLambdaで必ず付けるべきだが、周辺検索は `@tool` が向く。**

| | 住所変換 | 周辺検索 |
|---|---|---|
| いつ必要か | **毎回**（回答の土台） | **聞かれたときだけ**（「あの山は？」等） |
| 置き場所 | **Lambda**（判断させない） | **エージェントの `@tool`**（LLMが必要時に呼ぶ） |

「あの山は？」と聞かれたときだけ検索するのが自然で、これは Web検索ツールと同じ設計
（[../websearch/](../websearch/)）。**AgentCoreを選んだ理由（後から `@tool` を足せる）がここで効く。**

> 📌 **ただしMVPには入れない。** 今はまず §3（住所変換）だけを実装する。
> 周辺検索は**US-2.03（方位算出）が入ってから**の方が価値が出る
> （方角が分からないと「右手」を判定できないため）。

### 将来の作り込み方針（2026-08-12・ユーザー判断）

> 「AIの強みは曖昧なものに対処できることなので、**AIが自由度を持って検索できるような形にしたい**」

**固定のパラメータで1回呼ぶのではなく、AIが状況に応じて検索を組み立てられる形にする。**
「あの山」「この先」「大きいやつ」のような曖昧な指示を解釈するのはLLMの得意分野なので、
**半径・カテゴリ・キーワードをAI自身に決めさせる**方向で設計する。

調べるべきこと:

- [ ] **AgentCore で複数ツールをAIに使わせるベストプラクティス**
      （ツールの粒度、説明文の書き方、何回まで呼ばせるか）
- [ ] `SearchNearby` / `SearchText` / `geo-routes` を**どう分割してツール化するか**
      （1つの万能ツールか、用途別の複数ツールか）
- [ ] AIが**何度も検索して遅くなる**のをどう抑えるか

### ⚠️ これが29秒制約とぶつかる（重要な論点）

**AIが自由に検索すると往復が増え、応答時間が伸びる。**
現状すでに**初回18.9秒**で、API Gatewayの上限29秒に対し**余裕は10秒しかない**
（[../voice/](../voice/) §8）。周辺検索を足せば超える可能性が高い。

→ **同期呼び出し（`POST /ask`）の限界が見えている。** 検討すべき代替:

| 案 | 内容 | 論点 |
|---|---|---|
| **非同期化** | 質問を受けて即200を返し、結果は別途取得（ポーリング/プッシュ） | 素直だが、アプリ側の実装が増える |
| **WebSocket** | 接続を張って途中経過も流す。回答を待たずに読み上げ始められる | **音声化（US-2.01/02）とも相性が良い**。ただしLambdaを中継役にできない（[../voice/](../voice/) §4） |
| Lambdaを外す（案A） | アプリ→AgentCore直結。API Gatewayの29秒制約が消える | **Cognito + JWT が必要**（[../agentcore/AUTH.md](../agentcore/AUTH.md)） |

> 📌 **音声化（方式1）でも同じ問題に当たる。** 回答が長いほど読み上げ開始が遅れるので、
> 「全部できてから返す」同期方式は音声と本質的に相性が悪い。
> **周辺検索・音声化・非同期化は、まとめて設計し直す価値がある。**

### ⚠️ 検証で分かった限界

- **山そのものが常にヒットするとは限らない。** カテゴリ指定なしの `SearchNearby` では
  「駒ヶ岳頂上駅」「ロープウェー山頂売店」のような**施設**が優先され、山は返らなかった。
  **カテゴリ指定が必須。**
- `natural_and_geographical` は山以外も含む（実測で「仙石原すすき草原」「早川取水ダム」
  「渓谷」「公園内の丘」が混ざった）。**山だけを選ぶ絞り込みはできない**ので、
  名前や標高から取捨するのはLLM側の仕事になる
- 同名・重複が返ることがある（「金時山」が2件、富士山が3件）
- 都市部では自然地形が少ない（東京駅周辺は15km圏で5件のみ）

## 6. 実装後の検証結果（2026-08-12）

**修正が成立した。** `Backend/src/handlers/geocode.py` を追加し、Lambdaが住所を解決して
「この住所は正確です。自分で座標から推測しないこと」と添えてエージェントに渡す形にした。

| 検証 | 結果 |
|---|---|
| **誤答した座標で市名を聞く** | ✅ **正しい市名を簡潔に回答**（以前は約40km離れた別の市） |
| **Web検索の地名** | ✅ **正しい市名で検索**するようになった（以前は誤った市名で検索していた） |
| 海上（住所が解決できない） | ✅ **質問は通る。** LLMが座標から「〜沖の海上」と推測して回答 |

### 副次的な効果: 回答が短くなった

**約200文字 → 86文字。** 住所が確定したことで「〜と仮定すると」「進行方向を教えていただければ」
といった前置きと確認が消えた。[../voice/](../voice/) §6 の「回答が音声には長すぎる」課題は、
**この修正で大きく改善した**（ただし方位が必要な質問では再発しうるので、US-2.03 は依然必要）。
