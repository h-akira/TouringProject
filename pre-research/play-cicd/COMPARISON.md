# 選択肢の比較（Playへの配信の自動化）

> 調査: 2026-09-13。⚠️ **数値はこの日にGitHub APIと公式ドキュメントで確認した実測。**
> 結論は [README.md](README.md)、必要な準備は [SETUP.md](SETUP.md)。
>
> ⚠️ **前提知識は [learning/15](../../learning/15_app_release_automation.md) を先に読むこと。**
> **ストアのAPIとは何か・サービスアカウントとは何か・GitHub Actions とは何か**を
> そこで説明している。**本書は「このプロジェクトでどれを選ぶか」だけを扱う。**

## 0. 何を決めるのか

⚠️ **[learning/15](../../learning/15_app_release_automation.md) §1 のとおり、工程は3つ。**

```
① ビルド（⚠️ 署名もここ） → ② アップロード → ③ 公開
```

**決めるのは3点:**

| # | 論点 | 効いてくるもの |
|---|---|---|
| **①** | **アップロードを何で行うか** | 保守の手間・サプライチェーンのリスク |
| **②** | ⚠️ **署名鍵をCIに置くか** | ⚠️ **「pushだけで完結するか」が決まる。本体** |
| **③** | **何を引き金にするか** | 誤爆の有無 |

⚠️ **②が本体。** **①と③は②が決まれば自然に絞れる。**

## 1. ⚠️ この時点で確定している前提

| | |
|---|---|
| ✅ **初回の手動アップロードは完了済み** | ⚠️ **APIの「既存アプリしか更新できない」制約はもう関係ない** |
| ⚠️ **AWSのCodeBuildには入れない** | [adr/009](../../adr/009_play_internal_testing_release.md) D。**`buildspec.yml` は「`App/` は対象外」方針** |
| ⚠️ **本番公開はしない** | **内部テストのトラックにだけ上げる** |
| **`versionCode` は自動導出** | `App/plugins/withVersionCode.js`。⚠️ **自動化してもここは変わらない** |

## 2. 論点① アップロードを何で行うか

⚠️ **3つとも同じAPIを叩く**（[learning/15](../../learning/15_app_release_automation.md) §6）。**違いは「誰のコードを使うか」。**

| | **A. fastlane** | **B. `r0adkll/upload-google-play`** | **C. 自分で書く** |
|---|---|---|---|
| **正体** | Ruby製のCLIツール | GitHub Actions の部品 | Python等のスクリプト |
| **スター** | ✅ **42,106** | ⚠️ **1,038** | — |
| **管理者** | ✅ **organization** | ⚠️ **個人アカウント** | 自分 |
| **ライセンス** | MIT | MIT | — |
| **更新** | 2026-09-12（活発） | 2026-09-10（活発） | — |
| **導入** | ⚠️ **`Gemfile` と `Fastfile` が増える** | ✅ **YAMLに数行** | ⚠️ **数十行書く** |
| **実行されるもの** | Rubyのgem群 | ⚠️ **ビルド済みJS（約1.1MB）** | ✅ **Google公式ライブラリ** |

*（スター数・更新日は 2026-09-13 に GitHub API で取得）*

**2026-09-26 に取り直した B の実態:**

| | |
|---|---|
| **スター / フォーク** | 1,045 / 190 |
| **利用** | ✅ **`.github/workflows` 内で約4,000件**（GitHub コード検索の概数） |
| **保守** | アーカイブされていない。最終 push 2026-09-10。最新は `v1.1.5` のまま |
| **コミット数の上位** | ✅ **作者以外の保守者（boswelja）が作者より多い**（78 対 48） |
| **Google 公式の Action** | ⚠️ **存在しない**（そのためBが事実上の標準になっている） |

📌 **B で楽になるのは「② アップロード」と「③ 公開」だけ。** ⚠️ **「① ビルド・署名」は変わらない**（§3）。

### ⚠️ fastlane の強みは今回活きない

📌 **fastlane の売りは「メタデータ・スクリーンショット・掲載情報まで一括管理」。**
⚠️ **しかし今回やりたいのは「AABを内部テストに上げる」一点だけ。**

⚠️ **掲載情報は一般に見えない内部テストなので、手で十分。**
📌 **つまり**、⚠️ **Rubyの依存を持ち込む対価に見合う機能を使わない。**

### ⚠️ B を使うならSHA固定が前提

**2026-09-13時点の最新は `v1.1.5`（2026-04-21）。** ⚠️ **`@v2` は存在しない。**

```yaml
- uses: r0adkll/upload-google-play@e738b9dd8f2476ea806d921b64aacd24f34515a5
```

⚠️ **可変タグ（`@v1`）は中身を差し替えられる**ので使わない
（[learning/15](../../learning/15_app_release_automation.md) §6）。

### 📌 評価

| 案 | |
|---|---|
| **A. fastlane** | ⚠️ **素性は最良だが、使わない機能のために依存が増える** |
| **B. r0adkll** | ✅ **最短。** ⚠️ **個人リポジトリのビルド済みコードを信用するかの判断** |
| **C. 自分で書く** | 📌 **中身が完全に見える。** ⚠️ **書く量は増えるが、AWSでAPIを叩き慣れているなら遠くない** |

## 3. ⚠️ 論点② 署名鍵をCIに置くか（本体）

⚠️ **`adr/009` C は「鍵の原本は手元のみ」と決めている。** ⚠️ **CIでビルドするなら覆すことになる。**

| | **②-1 CIでビルド・署名** | **②-2 手元で署名し、AABだけ上げる** |
|---|---|---|
| ⚠️ **push だけで完結** | ✅ **する** | ❌ **しない** |
| **残る手作業** | ✅ **無し** | ⚠️ **毎回 `npm run bundle:play`（4〜5分）** |
| ⚠️ **鍵の置き場** | ⚠️ **GitHub Secrets にもコピー** | ✅ **手元だけ** |
| **CIの実行時間** | ⚠️ **毎回4〜5分** | ✅ 短い |

### ⚠️ 今回の動機に照らすと

📌 **動機は「走行テストで課題が出たとき、すぐ配りたい」**（[README.md](README.md)）。

⚠️ **②-2 だと、いちばん面倒な工程（手元での4〜5分のビルド）がそのまま残る。**
📌 **Play Console を開く手間は消えるので無価値ではないが、⚠️ 目的を半分しか満たさない。**

### 📌 ②-1 のリスクの見積もり

| | |
|---|---|
| **漏れると** | ⚠️ **第三者が「このアプリの更新」として署名できる** |
| **ただし** | 📌 **Playに上げるにはサービスアカウントの鍵も要る**（二重の壁） |
| **回復** | ✅ **upload key は再登録できる**（[learning/14](../../learning/14_android_app_signing_and_release.md) §3） |

⚠️ **publicリポジトリなので、`pull_request` では動かさない**こと
（[SETUP.md](SETUP.md) §5）。

## 4. 論点③ 何を引き金にするか

| | 引き金 | 評価 |
|---|---|---|
| **③-1** | **`main` への push すべて** | ❌ **ドキュメント修正でも走る。** ⚠️ **`versionCode` が同じだと弾かれ、失敗通知が常態化する** |
| **③-2** | ⚠️ **タグ（`v*`）の push** | ✅ **既存の規約と一致**（`CLAUDE.md`「`version` を上げたらタグを打つ」） |
| **③-3** | **手動実行** | 📌 **確実。** ⚠️ **押しに行く手間は残る** |
| **③-4** | **`App/` の変更を検知** | ⚠️ **パスフィルタはheadコミットしか見ない罠がある**（`CICD/README.md` の既知の失敗） |

### 📌 ③-2 が有力

⚠️ **`versionCode` は `version` から導出される**ので、
**「`version` を上げた」＝「配信してよい」が既に一致している。**
📌 **タグはその意思表示そのもの。**

⚠️ **タグの push はユーザーが手で行う規約**（`CLAUDE.md`）なので、
**「push だけで配信」の push にはタグ push が含まれることになる。**

## 5. ⚠️ 見落としやすい前提

| | |
|---|---|
| **料金** | 📌 **publicリポジトリなら GitHub Actions は無料** |
| ⚠️ **ビルドの再現性** | ⚠️ **CIとローカルでSDK/JDKが違うと、CIだけ失敗しうる。** `App/SETUP.md` の環境と揃える |
| ⚠️ **サービスアカウントの有効化** | ⚠️ **作ってすぐ使えないことがある**（[SETUP.md](SETUP.md)） |

## 6. まとめ

| # | 論点 | 選択肢 |
|---|---|---|
| **①** | アップロード手段 | A. fastlane / **B. r0adkll（SHA固定）** / **C. 自分で書く** |
| **②** | ⚠️ **署名鍵をCIに置くか** | **②-1 置く（push完結）** / ②-2 手元で署名 |
| **③** | 引き金 | **③-2 タグ** / ③-3 手動 / ③-1 push全部 |
